# Описание решения

Структура под четыре вопроса из условия. Заполняется по ходу, сейчас закрыт лексический этап.

## Какие данные и признаки использую и почему

Вся аргументация опирается на [EDA.md](EDA.md), здесь только итог.

**Текст объявления, все три поля.** Заголовок, разобранные параметры и описание.
Проверял по обучающим парам, какая доля токенов запроса встречается в тексте выбранного
объявления: по одному заголовку у 17.5% пар нет ни одного общего слова, с параметрами 9.2%,
с полным описанием 3.0%. Описание в одиночку сильнее, чем заголовок с параметрами вместе,
поэтому оно в индексе несмотря на длину.

**Параметры только в разобранном виде.** Сырой `item_infm_params_text` это 974 символа
без разделителей, где большая часть - служебные ключи («График работы от», «Тип стоимости
за услугу») и числа. Парсер оставляет значения, ключи и числа выбрасываются.

**Категории не использую.** `search_category` и `item_category_id` равны 114 почти везде,
`search_is_delivery_search` в бенчмарке равен нулю у всех 2 452 запросов. Реальная таксономия
одна, `item_microcat_id`, и она предсказывается по тексту запроса с точностью 90% в топ-3.

**География через координаты, а не через `location_id`.** У 17.4% запросов бенчмарка в их
`search_location_id` нет ни одного объявления корпуса: идентификатор иерархический, запрос
приходит с родительского узла. Центр поисковой локации восстанавливаю как медиану координат
объявлений, выбранных в ней по обучающим парам, и покрытие получается стопроцентным.

## Какие модели и алгоритмы применяю

**Разбор параметров через энтропию ветвления.** Словарь ключей свой в каждой из 752
микрокатегорий, руками его не собрать. Ключ стоит на границе двух сущностей, поэтому у него
разнообразны и левый, и правый контекст, а у куска внутри значения контекст предсказуем.
Поверх энтропии стоят требование минимальности, отсев числовых значений, отдельная обработка
начала строки и второй проход с маскированием адреса. Итог: 97 ключей, 99.6% строк
разбираются от первого ключа.

**Лексический поиск: BM25F, а не BM25 по склейке полей.** Длины полей отличаются на два
порядка: заголовок примерно 4 токена, параметры 140, описание 130. В склейке нормировка
считается по сумме, и вклад заголовка растворяется. BM25F нормирует каждое поле на свою
среднюю длину, складывает взвешенные частоты и применяет насыщение один раз к общей сумме.

**Гео-скор как логарифм отношения правдоподобий.** Из обучающих пар известно распределение
расстояний до выбранного объявления, из корпуса - до случайного. Логарифм отношения этих
плотностей и есть вклад расстояния в вероятность релевантности. Подбирать в нём нечего,
в отличие от произвольной убывающей функции с параметром.

## Как проверяю качество до отправки

Отдельный документ: [VALIDATION.md](VALIDATION.md). Коротко: из `train.parquet` собирается
копия бенчмарка того же размера, с той же долей знакомых обучению объявлений (9.6%) и с тем же
распределением запросов по длине и наличию фильтра. Каждое число сопровождается доверительным
интервалом бутстрэпом по запросам, потому что стандартная ошибка метрики здесь около 0.01
и приросты меньше этого неотличимы от шума.

Все проверенные гипотезы с числами - в [EXPERIMENTS.md](EXPERIMENTS.md).

## Какие типы ошибок нашёл и что с ними сделал

**Параметры как термы поиска ухудшают результат.** Добавление параметров к заголовку роняет
Recall@50 с 0.2773 до 0.2613. Причина в составе: родовые фасетные значения вроде «Ремонт
и отделка» общие для тысяч объявлений, совпадение по ним ничего не различает, а длину поля
раздувает. Решение: вес параметров 0.5 вместо 1, а фасетное совпадение выносится в отдельный
признак вместо подмешивания в лексический скор. По той же причине не работает дописывание
текста фильтра к запросу (0.3240 против 0.3255).

**Родовые однословные запросы.** Основной класс промахов. `кран` находится на 298 месте,
`грузчики` на 744, `брови` на 936. Под такой запрос подходят сотни объявлений с почти
одинаковым скором, а 48.6% корпуса вдобавок делит заголовок с другими объявлениями.
Текст внутри такой группы не различает ничего, различают гео и поведенческие признаки.

**Ограничение глубины отбора.** Из 2 913 релевантных объявлений 395 не попадают даже в топ-1000
по BM25 - и, вопреки первому впечатлению, в основном не из-за отсутствия лексического
пересечения. Запрос `педикюр` и объявление «Маникюр прочно, Педикюр, Наращивание» совпадают
дословно, просто подходящих объявлений больше тысячи. Отсюда решение не отбирать топ-N
с последующим переранжированием, а подмешивать гео в скор на этапе отбора.

**Пропуски в тексте.** У части объявлений корпуса описание пустое, и из parquet оно приезжает
как NA, которое переживает `astype(str)` и попадает в токенизатор как `float('nan')`. Эта
величина вдобавок истинная, так что проверка на пустоту её не ловила. Нормализатор теперь
проверяет тип, поля заполняются явно, на это есть тест.

## Воспроизведение

```bash
uv venv --python 3.12
uv pip install -e ".[dev]"
uv run avito-cg check-data
uv run avito-cg split
uv run avito-cg baseline
uv run avito-cg make-answer --out submissions/answer.csv
uv run avito-cg validate-answer submissions/answer.csv
```

Тяжёлые промежуточные результаты кешируются в `data/artifacts`, так что повторные запуски
идут секунды вместо минут. Порядок детерминирован: все случайные выборы идут от фиксированного
seed, при повторном запуске получается тот же `answer.csv`.
