# Описание решения

Четыре раздела ниже отвечают ровно на четыре вопроса из условия, в том же порядке,
в каком они там заданы.

Схема в одну строку: BM25F по трём полям отбирает кандидатов, к ним **на этапе отбора**
подмешиваются четыре калиброванных сигнала (гео, фасеты, микрокатегория, плотный поиск),
и топ-200 переупорядочивается градиентным бустингом.

| | | |
|---|---|---|
| Recall@50 на платформе | **0.8847** | пятая из семи попыток |
| Recall@50 локально | 0.9374 | [как устроен локальный бенчмарк](VALIDATION.md) |
| потолок текущего пула кандидатов | 0.9608 | выше не поднимет никакое переранжирование |
| время сборки ответа из готовых артефактов | 2 минуты | на ноутбуке без видеокарты |

## Какие данные и признаки использую и почему

Вся аргументация опирается на [EDA.md](EDA.md), здесь только итог.

**Текст объявления, все три поля.** Заголовок, разобранные параметры и описание.
Проверял по обучающим парам, какая доля токенов запроса встречается в тексте выбранного
объявления: по одному заголовку у 17.5% пар нет ни одного общего слова, с параметрами 9.2%,
с полным описанием 3.0%. Описание в одиночку сильнее, чем заголовок с параметрами вместе,
поэтому оно в индексе несмотря на длину.

**Параметры только в разобранном виде.** Сырой `item_infm_params_text` это 974 символа
без разделителей, где большая часть - служебные ключи («График работы от», «Тип стоимости
за услугу») и числа. Парсер оставляет значения, ключи и числа выбрасываются.

**Категории не использую.** `search_category` и `item_category_id` равны 114 почти везде,
`search_is_delivery_search` в бенчмарке равен нулю у всех 2 452 запросов. Реальная таксономия
одна, `item_microcat_id`, и она предсказывается по тексту запроса с точностью 90% в топ-3.

**География через координаты, а не через `location_id`.** У 17.4% запросов бенчмарка в их
`search_location_id` нет ни одного объявления корпуса: идентификатор иерархический, запрос
приходит с родительского узла. Центр поисковой локации восстанавливаю как медиану координат
объявлений, выбранных в ней по обучающим парам, и покрытие получается стопроцентным.
Точное совпадение `location_id` при этом осталось отдельным признаком переранжировщика:
оно несёт административную границу, которой в расстоянии нет.

**Популярность объявления - да, но осторожно.** Сколько раз объявление выбирали в обучающих
парах, это признак переранжировщика. Он опасен: в настоящем корпусе такая история есть только
у 9.6% объявлений, и на наивном сплите, где знакомы все 100%, он выглядел бы куда сильнее,
чем он есть. Поэтому локальный корпус собран с той же долей знакомых, 9.6%, а сам счётчик
нормирован на средний по знакомым объявлениям корпуса: локально разрешено 213 449 пар,
а на настоящих данных 497 673, и в абсолютных единицах признак бы не перенёсся.

**Признаки запросов бенчмарка использую, разметку нет.** Тексты запросов бенчмарка, их локации
и фильтры доступны легально и лежат в выданном файле. Я беру из них только распределения:
раскинг при сборке локального сплита подгоняет отложенную выборку под маргиналы бенчмарка
по локации, наличию фильтра и числу слов. Это перевзвешивание по наблюдаемым ковариатам.
Ни один ответ бенчмарка нигде не участвует, и ни одной строки `answer.csv` не получено иначе
чем прогоном модели.

## Какие модели и алгоритмы применяю

**Разбор параметров через энтропию ветвления.** Словарь ключей свой в каждой из 752
микрокатегорий, руками его не собрать. Ключ стоит на границе двух сущностей, поэтому у него
разнообразны и левый, и правый контекст, а у куска внутри значения контекст предсказуем.
Поверх энтропии стоят требование минимальности, отсев числовых значений, отдельная обработка
начала строки и второй проход с маскированием адреса. Итог: 96 ключей, 99.0% строк
разбираются от первого ключа.

**Лексический поиск: BM25F, а не BM25 по склейке полей.** Длины полей отличаются на два
порядка: заголовок примерно 4 токена, параметры 140, описание 130. В склейке нормировка
считается по сумме, и вклад заголовка растворяется. BM25F нормирует каждое поле на свою
среднюю длину, складывает взвешенные частоты и применяет насыщение один раз к общей сумме.

**Все дополнительные сигналы в одних единицах: логарифм отношения правдоподобий.**
Из обучающих пар известно распределение величины у выбранного объявления, из корпуса -
у случайного. Логарифм отношения этих плотностей и есть вклад величины в вероятность
релевантности. Подбирать в нём нечего, в отличие от произвольной убывающей функции
с параметром, и разные по природе сигналы становятся складываемыми. Так устроены гео,
фасетное покрытие и приор по микрокатегории.

**Слияние на этапе отбора, а не поверх усечённого топа.** Из 2 913 релевантных объявлений
первой версии сплита 395 не попадали даже в топ-1000 по одному тексту, и схема «взять топ-N и переранжировать»
отрезала бы их до всякого ранжирования. Поэтому сигналы подмешиваются ко всем ненулевым
позициям разреженной строки BM25.

**Плотный поиск: `intfloat/multilingual-e5-base`, дообученный на разрешённых парах.**
InfoNCE с негативами из батча, две эпохи. Намайненные тяжёлые негативы сознательно
не использую: самый тяжёлый лексический негатив здесь это объявление с тем же самым
заголовком в другой локации, а таких полкорпуса. Текстовый энкодер их не различит в принципе,
потому что различать нечего, и обучение на них даёт противоречивый сигнал. Разводит их гео.
Энкодер работает в двух ролях сразу: переупорядочивает найденное лексикой и приводит
кандидатов, до которых лексика не дотягивается.

**Разбор промахов воспроизводится командой.** `avito-cg errors` считает те самые таблицы,
из которых выросло переранжирование: размер эффекта по каждому признаку и долю попаданий
по корзинам расстояния, покрытия заголовка и числа близнецов. Построчный результат ложится
в `reports/errors.csv`.

**Переранжирование: CatBoost на топ-200 кандидатов, двоичная классификация со взвешенными
классами.** Обоснование пришло из разбора промахов.
Оба оставшихся класса потерь требуют условной поправки вида «ослабь гео, если текст совпал
отлично», а взвешенная сумма такого не выражает ни при каких весах, что я отдельно проверил
и записал как отвергнутую гипотезу. Признаки: скоры всех сигналов, их ранги внутри запроса,
расстояние, покрытие запроса заголовком и описанием (в том числе с весом по idf), совпадение
локации, свойства объявления.

Ранжирующую постановку (YetiRank с группировкой по запросу) проверял: она проиграла, 0.9330
против 0.9374, и считалась в семь раз дольше. Метрика вроде бы про порядок внутри запроса,
но позитив на запрос почти всегда один, и «упорядочить группу» вырождается в «поднять одну
строку», а это и есть взвешенная классификация. Смесь двух постановок дала +0.0014
при интервале, накрывающем ноль, и тоже не взята.

Открытый код, который использую: `scikit-learn`, `scipy`, `numpy`, `pandas`, `pyarrow`,
`catboost`, `transformers`, `torch`, предобученная модель `intfloat/multilingual-e5-base`
(лицензия MIT). Сам BM25F это Robertson, Zaragoza, Taylor, «Simple BM25 extension to multiple
weighted fields», 2004. Энтропия ветвления для разбора строк это Jin, Tanaka-Ishii,
«Unsupervised segmentation of Chinese text by use of branching entropy», 2006.
Внешних API нет, всё считается локально.

## Как проверяю качество до отправки

Отдельный документ: [VALIDATION.md](VALIDATION.md). Коротко: из `train.parquet` собирается
копия бенчмарка того же размера, с той же долей знакомых обучению объявлений (9.6%) и с тем же
распределением запросов по локации, длине и наличию фильтра. Каждое число сопровождается
доверительным интервалом бутстрэпом по запросам, а сравнения конфигураций между собой -
парным бутстрэпом по разностям, потому что обе конфигурации гоняются на одних и тех же
запросах и большая часть дисперсии у них общая.

Пять отправок дали пять точек калибровки: завышение 0.033, 0.087, 0.063, 0.059, 0.053.
Локальная оценка завышает примерно на 0.06, но не на константу, и зависимость содержательная -
завышение тем больше, чем большую долю итогового скора занимает гео. Разбор
в [EXPERIMENTS.md](EXPERIMENTS.md).

Отдельно стоит записать, чего эта проверка **не** умеет. Последний шаг - второй раунд
признаков переранжировщика - локально дал +0.0016 при интервале [-0.0011, +0.0045], то есть
от нуля неотличим, а на платформе +0.0104. Выборка в 2 452 запроса со стандартной ошибкой
около 0.01 эффекты такого размера просто не разрешает, и трактовать «незначимо локально»
как «не работает» нельзя. Правильная формулировка: локальный замер об этом шаге не сказал
ничего, ни в плюс, ни в минус.

## Какие типы ошибок нашёл и что с ними сделал

**Параметры как термы поиска ухудшают результат.** Добавление параметров к заголовку роняет
Recall@50 с 0.2773 до 0.2613. Причина в составе: родовые фасетные значения вроде «Ремонт
и отделка» общие для тысяч объявлений, совпадение по ним ничего не различает, а длину поля
раздувает. Решение: вес параметров 0.5 вместо 1, а фасетное совпадение выносится в отдельный
признак вместо подмешивания в лексический скор. По той же причине не работает дописывание
текста фильтра к запросу (0.3240 против 0.3255).

**Родовые однословные запросы.** Основной класс промахов на лексическом этапе. `кран`
находится на 298 месте, `грузчики` на 744, `брови` на 936. Под такой запрос подходят сотни
объявлений с почти одинаковым скором, а 48.6% корпуса вдобавок делит заголовок с другими.
Текст внутри такой группы не различает ничего, различает гео. Проблема закрыта: после слияния
доля попаданий перестала зависеть от числа близнецов по заголовку (дельта Клиффа +0.003).

**Ограничение глубины отбора.** Из 2 913 релевантных объявлений 395 не попадают даже в топ-1000
по BM25 - и, вопреки первому впечатлению, в основном не из-за отсутствия лексического
пересечения. Запрос `педикюр` и объявление «Маникюр прочно, Педикюр, Наращивание» совпадают
дословно, просто подходящих объявлений больше тысячи. Отсюда решение не отбирать топ-N
с последующим переранжированием, а подмешивать гео в скор на этапе отбора.

**Дальние объявления и нулевое лексическое покрытие.** Два оставшихся класса после слияния.
За 25 км доля попаданий падает с 0.92 до 0.46, при нулевом покрытии заголовка с 0.94 до 0.68.
Напрашивавшееся решение - ограничить штраф гео снизу - проверено и опровергнуто: метрика
ухудшается монотонно, потому что вместе с далёкими правильными в ответ лезут далёкие
неправильные, и вторых больше. Обе проблемы требуют условной поправки, а не правки кривой,
и это прямое обоснование переранжировщика.

**Пропуски в тексте.** У части объявлений корпуса описание пустое, и из parquet оно приезжает
как NA, которое переживает `astype(str)` и попадает в токенизатор как `float('nan')`. Эта
величина вдобавок истинная, так что проверка на пустоту её не ловила. Нормализатор теперь
проверяет тип, поля заполняются явно, на это есть тест.

**Реранкер упирается в пул, а не в себя.** Пять проверок подряд не дали ничего значимого:
девятикратный рост обучающей выборки +0.0029, гиперпараметры бустинга 0.0025 разброса,
второй раунд признаков +0.0016, смесь моделей +0.0014. При этом потолок пула 0.9608,
а мы внутри него на 0.9374. Оставшиеся 117 позитивов из 3 093 не попадают в топ-200 вовсе,
и это те же промахи - нулевое лексическое покрытие плюс большое расстояние. Дальше нужен
энкодер сильнее или кросс-энкодер поверх кандидатов, а не доработка ранжирования.

**Ошибка в собственной валидации.** Первая версия сплита согласовывала запросы по длине
и наличию фильтра, но не по локации, и локальный корпус вокруг запросов оказался вдвое
разреженнее настоящего. Гео на таком сплите выглядело умнее, чем оно есть. Нашёл до того,
как записал результат в журнал, починил раскингом по трём маргиналам сразу. Это сдвинуло
две уже снятые цифры и перевернуло знак калибровочного смещения.

## Воспроизведение

```bash
uv venv --python 3.12
uv pip install -e ".[dev]"
uv run avito-cg check-data
uv run avito-cg split
uv run avito-cg baseline
uv run avito-cg train-encoder          # нужен GPU, см. docs/KAGGLE.md
uv run avito-cg encode-corpus local
uv run avito-cg encode-corpus benchmark
uv run avito-cg fuse
uv run avito-cg donor-set
uv run avito-cg rerank --save "донор, logloss"
uv run avito-cg make-answer --out submissions/answer.csv
uv run avito-cg validate-answer submissions/answer.csv
```

Цепочка полная, и короче она не работает: без `encode-corpus` и `rerank` команда `make-answer`
отработает, но напечатает «плотный сигнал пропускаю» и «без переранжирования» и соберёт версию
на 0.90 вместо 0.9374. Единственный шаг, которому нужна видеокарта, это дообучение энкодера.

Тяжёлые промежуточные результаты кешируются в `data/artifacts`, так что повторные запуски
идут секунды вместо минут, а таблица признаков помнит, под какую конфигурацию собрана,
и пересобирается сама при её смене.

Всё, кроме одного шага, детерминировано: случайные выборы идут от фиксированного seed,
словарь ключей параметров закреплён в пакете, CatBoost воспроизводится бит в бит даже
при разном числе потоков. Пересборка ответа из готовых артефактов даёт тот же `answer.csv`
побайтово, это проверено прогоном.

Исключение - дообучение би-энкодера: на GPU часть операций backward складывает градиенты
атомарно, порядок сложения float зависит от планировщика, и веса расходятся уже на первых
шагах. Значит полный путь с нуля даёт эквивалентное решение, а не идентичные байты.
Разбор границы детерминизма - в [README](../README.md#где-детерминизм-кончается).
