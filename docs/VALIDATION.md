# Локальная валидация

```bash
uv run avito-cg split
```

Собирает копию бенчмарка из `train.parquet`, сверяет её с настоящим, проверяет на утечки,
гоняет две контрольные модели и сохраняет всё в `data/interim/local_benchmark/`.
Занимает около 70 секунд. Код в [`src/avito_cg/eval/benchmark.py`](../src/avito_cg/eval/benchmark.py).

## Зачем

Платформа даёт 7 попыток на 2 452 запроса. Подбирать по ним веса слияния и гиперпараметры нельзя:
попыток не хватит, и это прямое переобучение под тест. Значит нужна локальная копия, которая
предсказывает платформенный скор хотя бы по знаку изменений.

Наивный сплит «отложили запросы, взяли случайные объявления в корпус» врёт в двух местах,
и оба видны по цифрам из [EDA](EDA.md).

## Проблема первая: пересечение корпуса с обучением

В настоящем корпусе только **9.6%** объявлений встречаются в обучающих парах. Если набрать корпус
случайными объявлениями из train, знакомыми окажутся все 100%, и любой признак уровня объявления
(сколько раз его выбирали, его популярность) будет выглядеть сильнее, чем он есть на самом деле.
На реальном корпусе такого признака просто нет у девяти объявлений из десяти.

Проблема в том, что в train каждое объявление по определению хотя бы раз выбрано, то есть
незнакомых объявлений там нет вовсе. Их приходится создавать: часть запросов уходит
в **пул-донор**, их пары выбрасываются из обучения целиком, а их объявления идут в корпус
как незнакомые дистракторы.

Границу между обучающей частью и донором я не подбираю долями, а нахожу одним проходом.
Иду по перемешанным ключам запросов, переношу их в донор и держу для каждого объявления счётчик
оставшихся обучающих пар. Как только счётчик обнуляется, объявление становится незнакомым.
Останавливаюсь, когда незнакомых набралось столько, сколько нужно корпусу.

**Цена такого сплита.** Обучающих пар остаётся 214 941 из 497 673, это 43.2%. Остальные 279 657 пар
(199 362 запроса) уходят в донор. Это дорого, поэтому доля знакомых вынесена в параметр:

```bash
uv run avito-cg split --seen-share 1.0
```

вернёт наивный сплит со всеми парами в обучении. Так быстрее итерироваться, но абсолютные числа
будут завышены, и для финальных решений я пользуюсь значением по умолчанию.

Важная оговорка: не все компоненты решения чувствительны к этой доле. BM25, плотный поиск,
гео и классификатор микрокатегорий считают скор по содержимому объявления, и им всё равно,
встречалось ли оно в обучении. Чувствительны только признаки уровня объявления, и именно
из-за них сплит и устроен так.

## Проблема вторая: запросы бенчмарка другие

| | обучение | бенчмарк |
|---|---|---|
| слов в запросе, среднее | 2.45 | 3.20 |
| доля пустых фильтров | 35.2% | 63.1% |

KS-статистика по длине запроса 0.266. Если набрать отложенные запросы случайно, локальная выборка
получится короче и с фильтрами, а значит фасетный матчинг получит незаслуженно большой вес.

Поэтому запросы отбираются не случайно, а по совместному распределению **(пустой фильтр, число слов)**,
снятому с настоящих запросов бенчмарка. Разметки там нет, распределение признаков доступно
легально, так что это обычное перевзвешивание по наблюдаемым ковариатам, а не подглядывание
в ответы. Если в какой-то страте запросов меньше, чем просит распределение, беру сколько есть
и добираю недостачу из остальных.

## Что получилось

| величина | локальный | настоящий |
|---|---|---|
| запросов | 2 452 | 2 452 |
| объявлений в корпусе | 189 212 | 189 212 |
| слов в запросе, среднее | 3.185 | 3.197 |
| доля пустых фильтров | 0.631 | 0.631 |
| доля корпуса, знакомая обучению | 0.096 | 0.096 |
| локаций в корпусе | 2 318 | 2 877 |
| микрокатегорий в корпусе | 207 | 752 |
| релевантных на запрос, среднее | 1.188 | неизвестно |
| релевантных на запрос, ровно один | 0.891 | неизвестно |

Ещё одно число из meta: **24.8%** отложенных релевантных объявлений всё-таки встречаются
в обучающей части через другие запросы. Это выше корпусных 9.6%, и так и должно быть:
популярное объявление и выбирают чаще, и в обучение оно попадает вероятнее. На настоящем
бенчмарке эта величина не измерима, потому что разметки нет.

## Контрольные модели

Сплит без проверки самого сплита ничего не стоит, поэтому вместе с ним гоняются две модели,
которые нужны не ради качества, а ради того, чтобы убедиться в сходимости всей цепочки
«разметка - предсказание - метрика».

| модель | Recall@50 | 95% ДИ |
|---|---|---|
| случайные 50 | 0.00041 | [0.0000, 0.0012] |
| 50 ближайших по гео | 0.12209 | [0.1094, 0.1350] |

Случайный отбор должен давать примерно 50/189212 = 0.00026, и наблюдаемое значение накрывается
интервалом. Если бы там оказалось 0.01, значит в корпусе слишком мало дистракторов или в разметку
затекли лишние объявления.

Вторая строка интереснее: одна география, вообще без текста, даёт **0.122**. Это отправная точка,
с которой надо сравнивать всё дальнейшее.

## Проверка на утечки

`leakage_checks` возвращает список претензий, и пустой список это условие для того, чтобы
пользоваться сплитом. Проверяется:

- ни один отложенный запрос не попал в обучающие пары
- все релевантные объявления лежат в корпусе
- в корпусе нет дублей
- нет запросов без релевантных
- список запросов и разметка не разошлись
- достигнутая доля знакомых объявлений совпадает с заданной

То же самое покрыто тестами в [`tests/test_benchmark.py`](../tests/test_benchmark.py)
на синтетических данных, включая проверку, что перевзвешивание страт действительно
двигает выборку к целевому распределению, а не просто меняет seed.

## Чего эта конструкция не умеет

Честный список, потому что расхождение с платформенным скором ожидаемо и его причины надо знать
заранее.

1. **Корпус состоит из выбранных объявлений.** В train по определению попали только те, что
   кто-то однажды выбрал. Настоящий корпус это полный срез, включая объявления, которые
   не выбирал никто. Наши дистракторы «качественнее» настоящих, то есть задача локально
   может оказаться чуть сложнее по ранжированию и чуть легче по полноте.
2. **Микрокатегорий 207 вместо 752.** В train их всего 212, взять остальные неоткуда.
   Правда, по EDA 99.1% настоящего корпуса лежит в знакомых микрокатегориях,
   так что расхождение больше по разнообразию, чем по массе.
3. **Число релевантных на запрос неизвестно.** Локально получилось 1.188 против маргинальных
   1.40 по train, и это следствие перевзвешивания: у длинных редких запросов позитивов меньше.
   Что там на самом деле, без разметки не узнать.
4. **Один сплит это одна реализация.** Для важных решений стоит прогонять два-три seed
   и смотреть, переживает ли улучшение смену сплита.

## Как этим пользоваться

```python
from avito_cg.config import PATHS
from avito_cg.data.io import load_train
from avito_cg.eval.benchmark import LocalBenchmark
from avito_cg.eval.metrics import bootstrap_ci, recall_at_k, recall_per_query

train = load_train()
local = LocalBenchmark.load(PATHS.interim / "local_benchmark")

corpus = local.corpus(train)          # 189 212 объявлений, среди которых ищем
pairs = local.fit_pairs(train)        # только то, чем разрешено обучаться

predictions = my_model(local.queries, corpus)
print(recall_at_k(local.relevant, predictions))
print(bootstrap_ci(recall_per_query(local.relevant, predictions)))
```

Доверительный интервал тут не украшение. У 89% отложенных запросов ровно один релевантный
ответ, метрика ведёт себя как hit-rate, и её стандартная ошибка на 2 452 запросах около 0.01.
Улучшение меньше этой величины локально неотличимо от шума.
